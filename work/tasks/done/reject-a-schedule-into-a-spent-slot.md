## Why

Measured on 2026-10-30 against the published `fuzd` 0.12.0 CLI (`@fuzd/server` 0.12.1, `@fuzd/scheduler` 0.11.1) on a local anvil, while building template-commit-reveal's `with/fuzd` (stratagems' plan, step 8, item 5): a `scheduleExecution` into a slot whose batch had already been broadcast and finalised answered `success: true`, and the new transaction was never sent (the remote account's balance did not move), while the routes reported the slot broadcast and finalised with the FIRST batch's transaction.

The code explains it:

- `scheduleExecution` upserts the new record with `broadcasted: false, finalized: false` (`packages/scheduler/src/scheduler.ts:84-92`), and the storage overwrites every column on conflict (`packages/server/src/storage/RemoteSQLSchedulerStorage.ts:180`), so the spent slot is queued again (`getQueueTopMostExecutions` selects `broadcasted = FALSE`, `:187`).
- `execute()` then calls `executor.broadcastExecution` per batch index (`scheduler.ts:186-204`), which finds the existing executor row for `(chainId, account, slot, batchIndex)` and returns it with `slotAlreadyUsed: true` without sending (`packages/executor/src/executor.ts:208-216`). The scheduler ignores the flag and marks the slot broadcasted (`scheduler.ts:213-214`); the authors left a TODO for exactly this (`scheduler.ts:206-207`). `checkScheduledExecutionStatus` reads the old batch's finalised rows and marks it finalised (`scheduler.ts:550-555`).
- So the new transactions at batch indices the first batch already used are never sent. A LONGER new batch does send its extra indices, under a slot whose earlier transactions belong to another batch.

While the slot is still queued (nothing of it broadcast), replacing it is the intended behaviour and works.

The maintainer's decision (2026-10-30): reject it. Accepting it and broadcasting it as a new batch would also be coherent, but a slot that means "replace" before its broadcast and "add" after it is confusing.

## What to build

`scheduleExecution` in `@fuzd/scheduler` refuses a submission into a SPENT slot: one whose queued record is `broadcasted`, OR for which the executor holds a record at any batch index (`executor.getExecutionStatus({chainId, account, slot})`, which `checkScheduledExecutionStatus` made then; it now calls `executor.getExecutionStatuses` for a batch of slots). It throws before the upsert, so the server route answers HTTP 500 with `createErrorObject`'s body, `{success: false, errors: [{message, ...}]}`, the message naming `(chainId, account, slot)` as already used. This is unlike `broadcastExecution`, which answers success with the existing execution and `slotAlreadyUsed: true`; a schedule is refused outright. A slot that is merely queued (no executor record at any batch index) keeps being replaced, as today. A slot whose earlier schedule was archived without anything being broadcast is free and is accepted.

## Acceptance criteria

- [x] A schedule into a queued slot (no executor record at any batch index) replaces it: only the new batch is broadcast, as today.
- [x] A schedule into a slot already broadcast (pending or finalised) is refused: the route answers HTTP 500 with `{success: false, errors: [{message}]}`, the message naming the slot as used, nothing is stored, and the first batch's records are untouched.
- [x] A schedule into a PARTIALLY broadcast slot (some batch indices broadcast, the queued record not yet marked) is refused too.
- [x] A schedule into a slot whose earlier schedule was archived without any broadcast is accepted.
- [x] Tests cover these in the in-process server tests (`packages/server/test`: scratch database, mock RPC), driving `/internal/processQueue`; at minimum the already-broadcast-pending case, and the finalised one if the mock RPC is extended to answer receipts. `@fuzd/client`'s HTTP path then returns that body unchanged (note that its declared failure type, `{success: false; error}`, does not match the server's `errors`; fix the type or say why not), and its function-endpoint path throws instead; say which one a test covers.
- [x] A changeset for `@fuzd/scheduler` (and `@fuzd/server` if its code changes; it is otherwise bumped as an internal dependency), stating the bump level: this changes behaviour.

## Out of scope / known limits

- A slot freed by the admin prune routes (`deleteFinalizedScheduledExecutions`, `deleteFinalizedPendingExecutions`) is indistinguishable from a fresh one and is accepted again.
- A race with an in-flight `processQueue`: `execute()` holds the old record in memory and upserts it with `broadcasted: true` after broadcasting (`scheduler.ts:213-214`), so a schedule landing between the queue read and that write passes the new check and is then overwritten. A `WHERE broadcasted = 0` guard does NOT close it (the overwritten row is the new one, still unbroadcast). Closing it needs `execute()`'s write-back to be conditional on the row still being the record it read (a version column, or `checkinTime` plus a payload hash), with the `slotAlreadyUsed` check in `execute()` catching the newer record when it is processed next. Out of scope unless the builder chooses otherwise; record the choice in the done task.

- `@fuzd/scheduler` (`packages/scheduler/src/scheduler.ts`): `scheduleExecution` reads the queued record (`storage.getQueuedExecution`) and, unless that is already `broadcasted`, the executor's status for the slot (`executor.getExecutionStatus({chainId, account, slot})`). If either says something was broadcast, it throws before the upsert: `cannot proceed. the slot (chainId: <chainId>, account: <account>, slot: <slot>) has already been used: its execution has already been broadcast. schedule into a new slot.`. The server route turns it into HTTP 500 with `{success: false, errors: [{message, ...}]}`. The TODO in `execute()` is replaced by a comment saying why `slotAlreadyUsed` is still expected there (a retry of the same record after a partial broadcast) and naming the race left open.
- `@fuzd/executor` (`packages/executor/src/executor.ts`): `getExecutionStatus` answers `undefined` for a slot it holds nothing for. With the new check it would have refused every fresh schedule (measured: with this fix reverted, all five spent-slot server tests fail, the queued and archived cases included). Its other caller, `checkScheduledExecutionStatus`, relied on that wrong answer: a broadcast record the executor holds nothing for (an empty clear batch, which the schema accepts, or executor records pruned by `deleteFinalizedPendingExecutions` before the status check) was finalised through it. `checkScheduledExecutionStatus` now finalises such a record explicitly (`status === undefined`), so its behaviour is unchanged (found in review, see below).
- `@fuzd/client` (`packages/client/src/index.ts`): the failure that `scheduleExecution` and `broadcastExecution` return is typed `FailureResponse` (`{success: false; errors: {name?, message, code?, status?}[]}`, exported), the body the server sends and the HTTP path returns unchanged. `broadcastExecution` with a function `schedulerEndPoint` now returns that shape too (`errors: [{message}]`) instead of `{success: false, error}`.
- Tests: `packages/server/test/spent-slot.test.ts` (new) and one test added to `packages/client/test/schedule.test.ts`. The server test's mock node (`packages/server/test/utils/server.ts`) now has a clock the test moves forward (`chain.advanceTime`), records every raw transaction sent (`chain.sent`), and answers receipts for transactions the test has mined (`chain.mine()`: block 5 of 16, final with `finality=1`), plus `eth_getBlockByHash`. Every case drives `/internal/processQueue` to broadcast, on a scratch database with the mock RPC, and checks what the mock node received by decoding each sent raw transaction's recipient:

- **Broadcast, pending**: refused with HTTP 500 and one error whose message names the chain id, the account and the slot. The new submission is a longer batch (2 transactions), so the test also shows that the extra index is not sent. The queued record and the executor's index-0 record are deep-equal to before, and another `processQueue` sends nothing.
- **Broadcast, finalised**: reached through the extended mock: `mine()`, then `/internal/processTransactions` (the executor marks index 0 finalised) and `/internal/checkScheduledExecutionStatus` (the scheduler marks the slot finalised). ## Decisions

- **The check lives in `scheduleExecution`, in `@fuzd/scheduler`**, not in the server route or the storage. Every scheduler host (the node CLI, the Cloudflare worker) gets it, and it needs both the scheduler's storage and the executor, which only the scheduler holds. It runs after the existing validations (slot, chain, time, service parameters), just before the upsert, so a malformed schedule into a spent slot still reports its own error first.
- **"Spent" means the queued record is `broadcasted`, or the executor holds a record at any batch index of the slot.** The executor is consulted even when the queued record says not broadcast, which is what refuses the partially broadcast slot. It also refuses a slot spent by a direct `broadcastExecution` (the client test uses that), since it is the same executor record.
- **`getExecutionStatus`'s empty-slot answer was fixed in the executor**, not worked around in the scheduler (for example by calling the storage's batch read directly). The interface promises `undefined` for an unknown slot, and the scheduler only holds the `Executor` interface.
- **The race with an in-flight `processQueue` is left open**, as the task allowed: closing it needs `execute()`'s write-back to be conditional on the row still being the one it read (a version column, or `checkinTime` plus a payload hash), a schema change. The window is between `processQueue`'s queue read and the `broadcasted: true` write after the last broadcast. The comment that replaces the TODO in `execute()` says so.
- **Bump levels.** `@fuzd/scheduler` **minor**: a call that answered success now throws, which is breaking in 0.x even though the old success was never sent. `@fuzd/executor` **patch**: a wrong answer for an empty slot corrected to the documented one. `@fuzd/client` **minor**: the declared failure type changes (code that read `.error` stops compiling, though `.error` was always `undefined` over HTTP), and `broadcastExecution`'s function-endpoint failure changes shape at runtime. `@fuzd/server` gets no changeset (only its tests changed). Changesets' internal-dependency rule bumps it by a patch, with `@fuzd/tlock-decrypter` and the `fuzd` CLI (`changeset status`: client 0.13.0, scheduler 0.12.0, executor 0.11.2, server 0.12.2, tlock-decrypter 0.11.2, fuzd 0.12.1).
- **The client's declared type was fixed rather than documented.** It described a field the server never sends, so a TypeScript caller could not read the refusal message without a cast. `broadcastExecution` was fixed together with it because it had the same mismatch.

## Review

An independent reviewer (read-only subagent) read the commit against this record. It found:

- **P1, fixed:** the `getExecutionStatus` fix changed `checkScheduledExecutionStatus`, which then left a broadcast record with no executor rows unfinalised for ever. Such records stay first in `getUnFinalizedBroadcastedScheduledExecutions` (oldest `nextCheckTime`, never rewritten), so ten of them would starve the status check for everyone, and their payment reserves would keep counting in `/api/scheduling/reserved`. Fixed in `checkScheduledExecutionStatus` (it finalises a broadcast record the executor holds nothing for, as before), test-first with the test above.
- **P2, fixed:** a source comment cited this work/ file; the comment now carries the explanation itself.
- **P2, not fixed:** the client test's "no cast needed" typing claim is not checked by the gate, as vitest does not typecheck (it was checked by hand with `tsc --strict`). Making the gate typecheck tests is left to the maintainer.
- **Noted, outside this change:** `ArchivedScheduledExecutions` has `PRIMARY KEY (account, chainId, slot)`, so archiving a slot, scheduling into it again and archiving it again conflicts on the archive insert. Unchanged by this work (a re-schedule after an archive was accepted before), and recorded in `work/notes/observations/archive-a-slot-twice-conflicts.md`. An empty clear batch is also still accepted by the schema (`executions` has no `.min(1)`); refusing it is a separate change, not made here.

## Landed on main (2026-11-18)

The branch above was never merged, and `main` moved on under it (claims with a lease, guarded writes, the batched status check). It was ported by hand onto `main` at 0afcb0b rather than merged. What changed on the way:

- **The race with an in-flight `processQueue` is closed** (found in review of the port). The executor stores a slot's records only once it has sent them, seconds after a run claimed the slot (RPC requests, the broadcaster lock, a drand decryption first for a time-locked one), so in between the slot looked free: a schedule passed the check, its upsert released the run's claim (so the run's guarded write, `docs/adr/0004-claim-due-items-with-a-lease.md`, no longer overwrote it), and it was then never sent, the next run meeting the old batch with `slotAlreadyUsed`. `scheduleExecution` now writes with `SchedulerStorage.queueExecution`, one upsert that replaces the queued execution only if it is not broadcast and no run holds a live claim on it, and refuses otherwise: `cannot proceed. the slot (...) is being processed: its execution may be broadcasting right now. try again in a moment.` (the broadcast case gives the spent-slot message). Test: "a schedule into a slot a run is processing" in `spent-slot.test.ts` (red before: accepted, never sent). `parallel-processing.test.ts`'s re-schedule test now expires the run's claim first (a stuck run), the only way left for a schedule to take a claim over.
- **Two more gaps, closed after the port** (asked for):
  - A direct broadcast (`/api/execution/broadcastExecution`) into a slot the scheduler holds a queued schedule for is refused: `cannot proceed. the slot (...) has a queued schedule: broadcast into a new slot, or wait for the schedule.` It used to go through, and the schedule then met `slotAlreadyUsed` and was marked broadcast without being sent. The check is in the server route, which holds both storages (the executor does not know the scheduler). Except for the schedule's own transaction (a one-transaction schedule in clear, the same transaction: "send it now"): that is sent, and the schedule then finds it sent, as a retry of itself would (found in review: `tests/end-to-end/test/hono-client.test.ts` does exactly that, and a game may offer it).
  - What neither check can see beforehand is now caught when the schedule runs: a schedule accepted while a direct broadcast into the slot was in flight (seconds: the executor stores its record only after its RPC requests), or one written in the milliseconds before a run that broadcast part of the slot wrote it back. In `execute()`, a `slotAlreadyUsed` answer whose stored transaction differs from the schedule's (`sameTransaction`, now in `@fuzd/common`: key order, hex case and undefined fields ignored; the executor keeps a transaction as submitted through resubmissions and voids) means another execution took the slot: the schedule is archived with `lastError` `the slot (...) has already been used by another execution (batch index i): this one was not sent.`, and none of its other indices is sent (if earlier indices are on chain, the message says how many). A retry of the same record (same transaction) is still a continuation, as before. The executor's second check of the slot, under the broadcaster lock, now answers `slotAlreadyUsed` too (found in review: it returned the record unflagged, so a run that waited on the lock of a direct broadcast in flight took it for its own broadcast).
  - Why not closed atomically: that needs one reservation of the slot shared by both paths, before the seconds of RPC requests, for example a `ScheduledExecutions` row written by the direct broadcast, and that row would then be processed by the scheduler if the broadcast crashed. Detecting it at run time instead turns the silent loss into an archived schedule whose reason the account can read; the `success: true` the schedule got cannot be taken back.
  - Tests in `spent-slot.test.ts`: "a direct broadcast into a slot that holds a queued schedule is refused, and the schedule is broadcast" (red before: accepted, and the schedule never sent); "scheduled while a direct broadcast was in flight is archived, and nothing more is sent" and "written over a partially broadcast slot is archived, and its other indices are not sent" (red before: marked broadcast, and its second index sent under the spent slot); "run while the direct broadcast holds the broadcaster lock is archived too" (red before the executor fix: marked broadcast); "of the queued schedule's own transaction is sent now, and the schedule finds it sent" (red with the refusal applied to it).
- **The status check's empty-slot case is in `executor.getExecutionStatuses`** (the batched call `checkScheduledExecutionStatus` now makes, `work/tasks/done/status-check-throughput.md`): a slot without transactions counts as finalized there, so the second commit's `status === undefined` branch has no equivalent to port. The test for it ("a broadcast schedule the executor holds nothing for") passes unchanged.
- **The tests**: the `/internal/*` routes now need credentials, so `spent-slot.test.ts` sends the admin ones; `processTransactions` only checks transactions that are due, so the finalised case moves the chain's clock forward before it. The mock node's clock and mining were merged into the current harness (`MockRPCState.timeOffset` and `mined`, `server.chain`), which also counts calls and balances.
- Red first again on `main`: the pending, finalised and partial cases failed on `expected 200 to be 500`; the queued, archived and empty-batch cases passed. The verify gate, the nodejs, cf-worker and end-to-end suites passed after the port.
- **Changesets**: the three above; `refuse-schedule-into-spent-slot.md` now also covers the in-flight refusal and `queueExecution`, and names `@fuzd/server` (minor), whose code now changes. `@fuzd/server` also has `.changeset/archive-a-slot-twice.md`, from the follow-up `work/tasks/done/archive-a-slot-twice.md`.
